## TL;DR

A monolith, modular monolith, and microservices architecture are not three maturity levels. They place **code, data, deployment, and ownership boundaries** differently.

Start with the least distributed deployment model that meets the real constraints. Improve internal modularity before assuming a network boundary is necessary. Extract a service when **independent deployment creates measurable value**—for example, when it removes release coordination that is actually slowing a team, isolates a workload that must scale independently, creates a separately operated failure boundary, or gives one team ownership it cannot achieve inside a shared deployment.

The question is not "Can this be a service?" It is: **which specific constraint becomes easier to satisfy after this boundary becomes an independently deployed network boundary, and how will we measure that improvement?**

## Decision frame

Write down the forces before choosing an architecture label:

- How many teams need genuinely independent release schedules?
- Which business capabilities have stable ownership and materially different change rates?
- Which operations benefit from one local ACID transaction across several pieces of state?
- Which workloads need different scaling, availability, isolation, or runtime characteristics?
- Can the organization operate multiple independently failing deployments, data stores, dashboards, alerts, compatibility contracts, and on-call surfaces?
- Is current pain caused by coordinated deployment, or by poor module boundaries inside the codebase?
- What release-time, runtime, and incident-response outcome would improve if a boundary became a service?

A service boundary earns its cost when the independence it creates solves a named problem better than a local module boundary can.

## The options

### Monolith

A monolith is deployed as one application unit. It can be well modularized or tightly coupled; "monolith" describes deployment shape, not code quality.

Calls between modules can remain local, transactions can often stay inside one database boundary, deployment coordination happens around one deployable, and debugging does not inherently cross service networks. The trade-off is that all modules share the deployment lifecycle unless the deployment is later split.

### Modular monolith

A modular monolith keeps one deployment while enforcing explicit domain boundaries inside it. Modules expose deliberate interfaces, hide implementation details, and can have ownership/dependency rules even though they ship together.

This model is useful when teams need stronger code/domain boundaries but coordinated deployment is still acceptable. It also tests whether a proposed domain boundary is real: if the boundary cannot be kept clean inside one process/repository, moving it behind a network API usually preserves the conceptual coupling while adding distributed-system failure modes.

A modular monolith can be a long-lived architecture. It does not need to be justified as a temporary step toward services.

### Microservices

A microservices architecture moves selected domain boundaries into independently deployable services, usually with explicit network APIs/events and separately owned data or state boundaries.

That deployment independence can matter when different teams need separate release schedules, selected workloads need isolated scaling or availability policy, or one capability needs a different runtime/operational lifecycle. The cost is structural: local calls become remote calls, failures become partial, compatibility spans deployed versions, data consistency can cross transaction boundaries, and observability must correlate work across services.

## When each model fits

### Prefer a monolith when

- one team or a small number of closely coordinated teams own the product;
- the domain is changing quickly and stable service boundaries are not yet evident;
- coordinated deployment is not producing measurable delivery pain;
- local transaction/debugging simplicity matters more than independent service lifecycle;
- the organization has higher-value uses for operational complexity than adding independently operated services.

A monolith is not permission to create a ball of mud. Explicit modules, tests, dependency rules, and ownership boundaries still matter.

### Prefer a modular monolith when

- domain boundaries and code ownership need stronger enforcement;
- teams can coordinate one deployment even if they own separate modules;
- you want to reduce coupling before deciding whether independent deployment is necessary;
- important workflows still benefit from local transaction boundaries;
- there is not yet evidence that network/deployment independence pays for its additional correctness and operations cost.

This can remain the final architecture as long as those conditions hold.

### Prefer microservices when

- independent deployment solves a concrete, measured coordination problem;
- service boundaries align with durable business capabilities and clear owning teams;
- selected workloads require materially different scaling, availability, isolation, or release cadence;
- the organization can operate routing/discovery, telemetry, CI/CD, secrets, version compatibility, incident response, and asynchronous consistency across the intended number of services;
- the expected benefit of independence is observable enough to compare with the new distributed-system costs.

Examples of measurable value include shorter release lead time for the owning team, reduced coordination with unrelated teams, independently enforced capacity/availability objectives, or a smaller runtime blast radius for a capability.

## Microservices change the failure model

Inside one process, a normal function call completes under one runtime failure boundary. Across a service boundary, a caller can time out without knowing whether the remote operation failed before acting, succeeded but lost its response, or is still executing.

That ambiguity introduces design work around:

- timeouts and retry budgets;
- idempotency;
- partial failure;
- delivery semantics;
- distributed tracing/correlation;
- eventual consistency and compensating workflows;
- compatibility between independently deployed versions.

This is why splitting a module into a service is not a neutral refactor. It changes correctness and operations as well as deployment topology.

## Common traps

### Treating microservices as an organizational shortcut

A network boundary does not create a coherent business boundary or clear ownership. If the model is tightly coupled, service APIs can preserve that coupling while making changes and failures harder to coordinate.

### Mistaking repository size for deployment pressure

A large codebase may need module boundaries, build tooling, ownership, and dependency rules without requiring many deployables. Name the deployment constraint separately from the codebase-size problem.

### Using independent databases as an ideology

Service-owned data can improve autonomy when a service truly owns its business capability. But cross-service workflows must then model consistency and recovery explicitly. Splitting data without a concrete autonomy requirement can convert local transactions into distributed workflows without compensating value.

### Extracting before observing the pressure

Early boundaries often encode assumptions rather than durable capabilities. A modular codebase lets you gather evidence about ownership, release cadence, scaling, and failure isolation before committing to a network boundary.

## Practical heuristic

Ask these questions in order:

1. **Can better internal module boundaries solve the current problem?** Prefer that when deployment independence is not required.
2. **Which exact boundary needs independent lifecycle?** Name the release, ownership, scaling, availability, or isolation constraint.
3. **What changes when the call/data crosses a network?** Identify timeout, retry, transaction, consistency, and compatibility consequences.
4. **Who operates the new service during an incident?** Include dashboards, alerts, dependencies, runbooks, rollback, and ownership.
5. **How will we know the service boundary paid off?** Define a measurable release, scaling, reliability, or ownership outcome before extracting it.

The extraction threshold is reached when independent deployment creates measurable value that a local module boundary cannot provide at lower cost.

## Questions to ask before choosing

- Are the domain boundaries stable enough to defend with interfaces?
- Is coordinated deployment actually delaying releases or increasing risk?
- Which transactions would cross a service boundary?
- What happens when one side succeeds and the other side times out?
- How will traces/logs correlate one user action across services?
- Does each service have a durable owning team and incident responsibility?
- Are independent scaling/availability requirements observed or speculative?
- Could architecture tests enforce the desired boundary inside one deployment first?
- How many deployables can the current platform/on-call model operate reliably?
