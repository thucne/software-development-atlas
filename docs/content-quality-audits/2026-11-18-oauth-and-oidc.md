## Primary source, algorithm and illustrative-code checks

1. **OAuth and OIDC roles:** [OpenID Connect Core 1.0](https://openid.net/specs/openid-connect-core-1_0-18.html) builds an authentication/ID Token layer over OAuth 2.0; an ID Token is aimed at the Relying Party and cannot be substituted for a resource server's audience-restricted access token. Access token wire format is not universally a JWT. Valid signature is only one part of validation; issuer, audience, expiry, type, trusted keys, application policy and resource ownership still matter.
2. **Public PKCE:** [RFC 9700 §2.1.1](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.1.1) requires PKCE for public Authorization Code clients and recommends it for confidential clients. [RFC 7636](https://www.rfc-editor.org/rfc/rfc7636.html) describes high-entropy verifier and S256 challenge. No browser bundle or `client_id` can securely store a deployed client secret; PKCE does not authenticate a public client. The sequence diagram is explicitly scoped to a direct browser client; with a BFF the authorization response traverses the browser but code exchange/token storage remain on the server.
3. **Mix-up and CSRF:** [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.1) differentiates browser-bound PKCE, OIDC `nonce` and correctly bound `state`; their permitted CSRF protections are conditional. For clients integrating multiple ASes, [RFC 9207](https://www.rfc-editor.org/rfc/rfc9207.html) defines the authorization-response `iss` parameter and requires issuer identity matching; use alternate mix-up mitigations under the BCP only if conditions are satisfied. None supersedes resource-level authorization.
4. **Browser architectures:** [RFC 10017 §6](https://www.rfc-editor.org/rfc/rfc10017.html#section-6) compares BFF, token-mediating backends and browser-only clients with decreasing token exposure protections. In a BFF, tokens stay server-side and protected cookie sessions are exposed to the browser; injected same-origin JavaScript may still send authenticated requests, so cookie CSRF protection, application authorization and XSS defenses remain essential.
5. **Refresh token safety:** [RFC 10017 §6.3.2.3](https://www.rfc-editor.org/rfc/rfc10017.html#section-6.3.2.3) and [RFC 9700 §2.2.2/§4.14](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.2.2) require an issuer of refresh tokens to a *public client* to rotate them or sender-constrain them, and impose maximum lifetime or inactivity expiry; an absolute end-of-life established at initial issuance cannot be silently extended indefinitely by rotation. The authorization server may decide not to issue browser refresh tokens. Rotation is a misuse-detection mechanism, not proof an attacker already controlling same-origin JavaScript is defeated.
6. **Discovery and example correctness:** [RFC 8414](https://www.rfc-editor.org/rfc/rfc8414.html) and OIDC discovery support documented issuer and JWKS endpoints. Three Mermaid diagrams describe trust flows, not concrete HTTP network captures. An illustrative JWT-looking ID token passed to a resource server cannot be accepted solely because its signature validates; the incident is explicitly hypothetical with no fabricated numbers or provider postmortem. The self-check correctly rejects inferring authorization from an unverified decoded payload or a claimed admin role.
