## Claim, source and example matrix

1. **Illustrative payment arithmetic:** Original hypothetical EN $200 scenario said initial payment + automatic retry + two additional taps, then asserted **three** payments / $600. The VI opening similarly used 2 million VND and 6 million but described four attempts. Rewritten EN/VI as a single **$200** checkout with **three total network requests**: first, one automatic retry, one further manual resubmission. Without deduplication this **may**, not must, cause up to three distinct $200 charges ($600). No observed incident, exact timing, operator loss or user dispute is claimed.
2. **HTTP method semantics:** RFC 9110 §9.2.2 defines idempotency by identical requests' **intended effect**; status, incidental logging and actual API correctness are separate. A `PUT` with repeated charges can violate the application contract. A `POST` can have a stronger endpoint-specific duplicate-safety protocol without changing HTTP method semantics.
3. **Current IETF draft (P1 freshness fix):** Previous text claimed `draft-ietf-httpapi-idempotency-key-header-07` expired 2026-04-18 and implied no current draft. The IETF now publishes **active `-08`**, dated **2026-10-22**, expiring **2027-04-25**. This is **still an Internet-Draft, not an approved RFC**. Both EN/VI texts and references are updated after reading its requirements, examples and working-document status.
4. **Structured Field value:** The `-08` draft specifies `Idempotency-Key` as an RFC 9651 **Structured Field Item of String type**. Thus the previous bare `Idempotency-Key: 3e8a3c8f-...` was not a well-formed string instance under the current draft. Updated EN/VI code examples to the same full quoted illustrative UUID: `Idempotency-Key: "3e8a3c8f-4f32-4474-b7fa-5f9760dd67b4"`. Existing provider APIs may use other header parsing rules; the draft cannot retroactively impose interoperability on them.
5. **Fingerprint optionality:** The `-08` draft says the server **MAY** calculate a request fingerprint; previous TL;DR misleadingly implied a cryptographic SHA-256 fingerprint must always accompany `INSERT ... ON CONFLICT`. New text frames normalized semantic comparison and SHA-256 as optional implementation choices. If the endpoint promises key/payload comparison, it must specify which fields establish sameness, avoiding raw JSON ordering and volatile metadata.
6. **Atomic reservation and concurrent behavior:** Traced `if not exists(key) -> charge -> insert(key)` and the Mermaid state diagram: two concurrent requests can both pass a non-atomic check. A durable scoped unique reservation is needed before the duplicate-sensitive effect; a local DB transaction can bind an order and operation record but **cannot** roll back a provider charge. In-progress duplicates need defined wait/conflict/poll semantics. No live SQL fixture or payment call was run; snippets are labeled conceptual and evidence is trace-based.
7. **External side effects, outcome and retention:** A response lost after a provider charge requires downstream stable identity or reconciliation, not a fresh independent charge. Stripe's **API v1** documents storing first completed response status/body including 500 after execution starts and comparing repeated parameters; Stripe API v2 has different retry behavior. These are provider examples, not universal protocol requirements. A hypothetical 24-hour record retention bounds replay; domain uniqueness constraints may protect the business invariant longer.
