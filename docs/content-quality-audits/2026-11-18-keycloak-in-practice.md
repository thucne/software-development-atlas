## Technical correctness and concrete examples

1. **Keycloak realm/client vs resource server:** [Keycloak Server Administration Guide](https://www.keycloak.org/docs/latest/server_admin/) treats a realm as a security boundary and OIDC/SAML clients as registrations; realm and client roles are *authorization input*, not automatically enforced per-resource permission checks. The imagined admin token cross-service incident is explicitly labeled hypothetical; one realm-issued JWT signature does not authorize use at every audience.
2. **Public client and PKCE default:** [Keycloak JavaScript adapter](https://www.keycloak.org/securing-apps/javascript-adapter) says browser-side JavaScript cannot keep a client secret; current adapter defaults to Standard Authorization Code with `pkceMethod: 'S256'`. [Keycloak 24 release notes](https://www.keycloak.org/docs/24.0.0/release_notes/) document the default transition. It is *version/adapter configuration specific*, not a universal OAuth property; still test actual `keycloak-js` version and effective flow. PKCE does not authenticate the public client or replace redirect/issuer validation.
3. **High-impact Bearer mistake corrected:** The original bullets said the access token is attached when calling APIs, which could imply `keycloak-js` auto-injects credentials. Official adapter documentation's `fetch` example explicitly sets `authorization: Bearer ...` in application code and recommends `updateToken()` before calling protected services. Both lessons now show guarded `keycloak.authenticated`, `updateToken(30)`, token presence, and a manual `fetch` `Authorization` header. No client secret enters browser code. The TypeScript example is conceptual and uses fictional `example.com` addresses, with HTTP handling omitted; no live Keycloak server or browser session was executed.
4. **Modern browser and logout limits:** The Keycloak adapter documentation's tracking-protection section says third-party cookie blocking can disable the Session Status iframe, change silent `check-sso` to a redirect or disable it, and defer cross-window sign-out detection until token refresh. This is conditional browser behavior, not guaranteed immediate logout. Synced both languages, update checklists and diagram notes to prevent readers assuming every API request queries Keycloak for JWKS.
5. **Client scopes, mapping and external IdP:** Client scopes and protocol mappers determine OIDC token claims and SAML assertion attributes; client role vs realm role namespace and Keycloak identity brokering vs LDAP user federation are different ownership boundaries. The example role mapping is illustrative; token format/audience/profile, expiry and application policy still require API-side enforcement.
6. **Browser architecture:** [RFC 10017](https://www.rfc-editor.org/rfc/rfc10017.html#section-6) ranks BFF higher for direct token exposure protection among its three browser patterns, but same-origin malicious JavaScript may still send authenticated requests using a BFF cookie session. BFF introduces cookie/CSRF and backend resource responsibilities; not a silver bullet. This matches the paired OAuth/SSO Atlas lessons.
7. **Exercises, visuals, links:** Traced all three diagrams as conceptual trust maps, the sample JavaScript/TypeScript initialization and guarded token request (static API contract only), and the finance department ID-token-to-Orders-API self-check. Both answers correctly prohibit using an OIDC ID Token as a resource-server access token. Existing source/route references and related lesson links retained.
