## Technical claims and primary-source review

1. **401 vs 403/404:** [RFC 9110 §15.5.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.2) specifies that a sender of `401` **MUST** include `WWW-Authenticate` with an applicable challenge. A server with otherwise valid credentials can deny with 403; [§15.5.4](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.4) allows, but does not require, 404 for deliberate resource concealment. Corrected EN/VI text previously saying 401 'normally' has the challenge.
2. **CORS and preflight:** [WHATWG Fetch](https://fetch.spec.whatwg.org/#http-cors-protocol) separates response-sharing policy from the backend authentication result. Preflight applies only when required by method/header conditions; `Authorization` normally requires it for cross-origin fetch. A credentialed `include` request cannot share a response with `Access-Control-Allow-Origin: *`; it requires matching explicit origin and `Access-Control-Allow-Credentials: true`. The Mermaid sequence now identifies a conditional preflight rather than an implied universal OPTIONS call. A failed OPTIONS can prevent sending the actual request.
3. **OIDC trust and Keycloak:** [Keycloak OIDC guide](https://www.keycloak.org/securing-apps/oidc-layers) and [JavaScript adapter](https://www.keycloak.org/securing-apps/javascript-adapter) document specific redirect URI/Web Origins setup, issuer realm keys and browser adapter constraints. Token signature alone does not establish audience or API authorization. Unknown `kid` handling must refresh only trusted issuer JWKS with bounds, never disable signature verification or fetch attacker-selected untrusted key URLs.
4. **SPA vs BFF:** [RFC 10017 (August 2026, BCP 212)](https://www.rfc-editor.org/rfc/rfc10017.html) distinguishes browser client and backend-mediated architectures. An OAuth exchange in a BFF can occur server-side and be absent from DevTools; JWT validation may use cached keys rather than making a JWKS HTTP request on every incoming API call. The diagram is an architectural boundary map, not a literal universal request-by-request sequence.
5. **Sessions, CORS, logout:** `HttpOnly` prevents JavaScript cookie access, not cookie transmission; `SameSite`, `Secure`, `Domain`, `Path` and cross-origin `credentials` are separate constraints. [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) and RFC 10017 support distinguishing IdP SSO state, app local sessions, logout and refresh-token ownership.
6. **Worked example and code:** traced the Keycloak JSON object `realm_access.roles: [employee]` versus `resource_access.orders-api.roles: [refund]`, as valid JSON, and a constructed refund 403 where the API looks up client roles but the token only provides the realm role. Role placement is provider-specific; API resource authorization still requires server enforcement. The invented 'week of CORS changes' story is now explicitly **hypothetical**, without purported measured outage duration or first-party incident claim.
7. **Self-check:** analyzed the case where Network shows underlying API 401 but browser hides it due to absent CORS response headers; fixing sharing reveals the authentication response and does not fix the separate credential problem. No live Keycloak realm, browser network capture, authorization server or external provider was executed for this review. This is a standards-based, static model/explanation audit.
